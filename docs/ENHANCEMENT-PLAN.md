# Product, POS and credit enhancement plan

Preserve the existing React/NestJS/Prisma/PostgreSQL architecture, original record IDs, posted history, expiry acknowledgements, role policies and stock ledger. Work on a development branch and validate migrations against an isolated database before applying any change to an existing store.

1. **Product/inventory:** add a normalized master-data catalogue for categories, dosage forms, product types, customer types and units; backfill existing strings to linked records; retain legacy text/packaging fields for compatibility. Add product tracking policies, specifications and product-specific unit conversions. Store quantity/conversion values as NUMERIC(24,6), migrating integer values without changing their magnitude. Keep actual historical batch costs and conversion snapshots.
2. **POS:** centralize unit/price resolution and multi-item validation; make MRP a warning with an audit record; add per-cashier database-backed drafts/held carts with revision checks and price/stock/expiry revalidation. Drafts never reserve stock.
3. **Payments/credit:** append-only customer ledger, immutable collections and settlements, per-invoice receivable projections, explicit customer advances, idempotent split payments and controlled returns/reversals. Debit increases the net amount owed; credit reduces it. Gross invoice outstanding and unallocated advances remain separately visible; their difference reconciles to the ledger. Collections do not create sales revenue or profit.
4. **Invoices/dashboard:** one consistent invoice model rendered as 58 mm, 80 mm and A4 PDF with original invoice numbers, customer/cashier, allocations, paid/due/change, and configurable notes. Add purchase-cost versus potential selling-price inventory values and credit/collection indicators.
5. **Verification/delivery:** real PostgreSQL regression and new integration tests, browser workflows, production build, Windows Docker migration/start/backup checks. Document migrations, permissions, accounting conventions and limitations. Commit/push the development branch for review; do not force-push or merge into main without review.

Serial-tracked stock must use integral base units and explicitly trace received/sold/returned serials. Non-expiry products use an internal no-expiry sentinel while the UI displays “Not applicable”; pharmaceutical tracking cannot be weakened after history exists. Payment transfer references are recorded as operator-entered, never externally verified. Store only card last-four digits and references, never full card numbers or CVV.
